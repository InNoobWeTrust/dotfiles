# Skill portability: capabilities, not sibling identities

**User correction:** renaming one supposedly self-contained skill exposed required
edits throughout other skills and docs. Repairing those references fixed the rename,
not the coupling. The user explicitly requested capability-based portability for
all skills and durable recording in project docs and memory.

**Apply when authoring, modifying or auditing reusable guidance:**

- Operational handoffs describe capability, inputs, output/evidence, authority and
  absence behavior. Do not depend on another skill's identity, directory or continued
  installation. The current agent or an authorized capable owner may supply the work.
- Keep essential methods and stops local or specify an actionable required-input
  contract. Vague “use an available capability” language must not erase approval,
  independence, checkpoint, evidence or non-continuation requirements.
- Bundle-relative resources are valid. Check deep references, templates, scripts
  and CSV assets, not just the main skill file. Resolve paths from the loaded bundle,
  not this dotfiles checkout or an assumed home directory.
  Include bare pack-document paths and named governance rules in the audit; a
  sibling-name scan alone misses those hidden prerequisites.
- Concrete names belong in installation/discovery/composition maps and explicit
  pack-selection manifests. Own identity and genuine scoped products/APIs may remain
  named; these are not incidental sibling dependencies.
- Verify a copied-alone bundle and a scratch sibling rename, plus native/integration/
  absent-capability walkthroughs. A link check inside the full pack is insufficient.
  Source checks do not prove runtime agent compliance or productivity gains.

See [Portable skill bundles](../../docs/skills-and-rules/skill-portability.md) for
maintainer guidance. This entry records the requested lesson, not task acceptance,
an empirical success claim, or permission for automatic consolidation or installs.
